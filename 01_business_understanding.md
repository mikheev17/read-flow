# Бизнес-анализ (Business Understanding)

> ReadFlow - это AI-сервис (mobile/web), который помогает читать книги на английском через:
> - контекстные объяснения
> - адаптацию сложности
> - запоминание слов

## Описание

Люди хотят читать книги на английском, но быстро теряют интерес: текст кажется слишком сложным и медленным, перевод ломает погружение, а слова плохо запоминаются.

Главная проблема - не отдельные слова, а когнитивная нагрузка и потеря потока чтения (flow).

ReadFlow решает это как задачу адаптивного понимания текста: в реальном времени определяет, где читателю трудно, и мягко вмешивается - объясняет выражения в контексте, упрощает сложные фразы, подстраивает текст под уровень и помогает закреплять лексику.

Результат: человек читает без постоянных переключений на переводчик, сохраняет ритм и дольше остается в чтении.

- Взрослый пользователь, изучающий английский язык на уровне A2-B2.
- Регулярно читает или пытается читать художественные и нон-фикшн тексты в оригинале.

**Primary**

**Secondary**

### Существующие решения (5 ближайших по ML-функциональности)

| Решение | ML/AI-функции | Сильные стороны | Ограничения относительно ReadFlow |
|------|---------------|------------------|-----------------------------------|
| LingQ | Персонализация по истории слов, рекомендации, SRS | Зрелый reading UX, сильный словарный контур | Слабая адаптация интервенций на уровне абзаца |
| Readlang | Контекстный перевод, AI-объяснения, SRS | Очень быстрый сценарий чтения web-контента | Ограниченный deep-reading сценарий для длинных книг |
| Sentia Read | CEFR-адаптивные объяснения, контекстные подсказки | Близкий к ReadFlow формат "читать и понимать в потоке" | Ранняя зрелость продукта и ML-качества |
| LingoBlend | Частичный AI-перевод по уровню, grammar hints, SRS | Хороший фокус на comprehensible input | Недостаточно подтвержденные retention-метрики |
| Duolingo (Max) | GPT-фичи, адаптивные упражнения, персонализированный фидбек | Сильная ML-персонализация и удержание | Основной сценарий не про чтение длинных книг |

#### Почему рынок все еще не закрывает задачу ReadFlow
- **Нет замкнутого ML-контура "difficulty -> knowledge -> policy -> outcome":** обычно есть 1-2 функции (перевод/SRS), но не полный контур управления чтением.
- **Слабая персонализация в реальном времени:** мало кто адаптирует сложность и тип интервенции на уровне конкретного абзаца и состояния пользователя.
- **Недостаток flow-aware механики:** большинство решений либо "читалка", либо "тренажер"; редко оптимизируют именно непрерывность чтения длинного текста.
- **Ограниченная глубина контекста:** объяснения часто локальны (слово/фраза), без устойчивой модели того, что пользователь уже понял в текущей книге.
- **Слабая связка с бизнес-метриками удержания в чтении:** немногие продукты явно оптимизируют `completion rate` книги и `D7/D30 retention` читателя.

#### Позиционирование ReadFlow относительно конкурентов
- **Ближайшие по ML-контуру:** `LingQ`, `Readlang`, `Sentia Read`, `LingoBlend`, `Duolingo (Max)`.
- **Инфраструктурный substitute:** `Kindle + переводчик + Anki` (ручной стек без единой адаптивной системы).

**Вывод для product strategy:** у ReadFlow есть окно дифференциации в построении именно **adaptive reading engine**, где ML оптимизирует не отдельные упражнения, а непрерывный прогресс пользователя в чтении реальных книг.


## 1.1 Текущая ситуация (Assessing current solution)

### Ресурсы и инфраструктура

**Инфраструктура (MVP)**
- Облако: `Yandex Cloud` или `Timeweb Cloud` (старт с одним провайдером для снижения операционной сложности).
- Подход к запуску: container-first (`Docker`) с возможностью последующего перехода на managed orchestration.

| Компонент | Решение для MVP | Зачем нужно | Масштабирование (этап 2+) |
|------|------------------|-------------|----------------------------|
| Backend API (Go) | `Docker` + `VM/Compute` | Основная бизнес-логика, авторизация, оркестрация ML-сервисов | Переход на managed Kubernetes / autoscaling group |
| База данных | `PostgreSQL` (managed или self-hosted) | Профили пользователей, прогресс, события чтения, словарь пользователя | Реплики, партиционирование event-таблиц, read replicas |
| Кэш / сессии | `Redis` | Быстрый доступ к состоянию сессии и временным данным интервенций | Кластер Redis, разделение на cache и queue |
| ML/LLM слой | Внешний LLM API + локальные эвристики/модели | Генерация объяснений, упрощение текста, контекстные подсказки | Гибрид: роутинг между провайдерами, fallback open-source модели |
| Хранилище файлов | `Object Storage (S3-compatible)` | EPUB/тексты, промежуточные артефакты, логи выгрузок | Versioning, lifecycle policies, CDN |
| Аналитика и логи | Event logging + `ClickHouse/BigQuery` (по бюджету) | Метрики retention, completion, интервенций и A/B тестов | Near-real-time pipeline, продуктовые дашборды |
| Мониторинг | `Prometheus + Grafana` или cloud-native мониторинг | SLA API, latency, error rate, стоимость inference | Алерты по SLO и cost guardrails |
| CI/CD | `GitHub Actions` | Автосборка, тесты, деплой в staging/prod | Progressive delivery, canary для ML/policy |

**Минимальный контур окружений**
- `dev`: быстрая разработка и интеграционные проверки.
- `staging`: smoke-тесты перед релизом, проверка ML/LLM quality.
- `prod`: ограниченный пилот, наблюдение за `D1/D7 retention`, `session duration`, `completion rate`.

**Нефункциональные требования для MVP**
- Доступность API: целевой `uptime >= 99.5%`.
- Производительность: p95 latency для основных операций чтения/подсказок <= `800 ms` (без учета долгих LLM-вызовов).
- Безопасность: шифрование данных в transit (`TLS`) и at rest, базовый RBAC, регулярные бэкапы БД.
- Экономика: лимиты на LLM-запросы на пользователя, кэширование повторяющихся объяснений, мониторинг cost per active user.

## 1.2 Решаемые задачи с точки зрения аналитики (Data Mining goals)

> Ключевая цель: поддерживать поток чтения, а не проверять знание отдельных слов.

Центральная постановка: `P(struggle | text, user_state, context)` — вероятность, что пользователь испытывает затруднение на текущем фрагменте.

### 1.2.1 Минимальный ML-контур MVP

1. **Difficulty model (отдельная ML-задача):** предсказание `difficulty_score` для фрагмента текста (regression/ordinal classification по CEFR-уровням).
2. **Struggle model:** оценка `P(struggle)` по поведенческим сигналам (паузы, возвраты, скорость чтения, клики по подсказкам).
3. **Policy model:** выбор действия (`no_action`, `hint`, `explanation`, `simplify`) с лимитом интервенций.
4. **LLM layer:** генерация текста интервенции по выбранному действию (LLM не принимает решение, только исполняет).

### 1.2.2 Что не делаем в MVP

- Не запускаем отдельные тяжелые модели `Knowledge Tracing` и `Engagement`.
- Используем их сигналы как признаки в `state` policy-модели.
- Делаем упор на implicit feedback и быстрые продуктовые итерации.

### 1.2.3 Метрики и обучаемость

- **North Star:** `Retention (D7/D30)` и `completion rate` книги.
- **Difficulty model:** MAE/RMSE (для regression) или QWK/F1 (для CEFR-классов).
- **Struggle model:** AUC/PR-AUC + калибровка.
- **Policy:** online-метрики (`session duration`, `continue reading`) и bandit-оценка (`IPS`, `Doubly Robust`).
- **Simplification:** `SARI` + доля продолжения чтения после интервенции.

### 1.2.4 Онлайн-пайплайн

`read -> signals -> P(struggle) -> policy action -> LLM intervention -> log outcome`

Логируем минимум: `state`, `action`, `propensity_score`, `immediate_reward`, `delayed_reward`, `timestamp`.

### 1.2.5 Итог

Переход от набора разрозненных моделей к единому контуру:  
`P(struggle) -> Policy -> Action -> Retention`.

### Фазы и оценка

| 4. Modeling | MVP на LLM + baseline ML (`struggle`-модель и policy-rule engine) | 3-4 недели | ML Engineer |
| 5. Evaluation | Offline OPE (`IPS/DR`) + Online A/B-тесты | 2 недели | ML Engineer + Product Owner |
| 6. Deployment | API, Telegram bot / mobile integration, логирование и мониторинг | 2 недели | Backend Engineer + Frontend/Mobile Engineer |

**MVP-стратегия**
- **Самый быстрый MVP (без heavy ML):** LLM через API, `SUBTLEX` как словарь сложности, простые эвристики для интервенций.
- **MVP+ (умнее):** добавить data-driven контур персонализации:
  1. **Struggle Model**
     - Оценивает вероятность затруднения на уровне фрагмента (`P(struggle | state)`).
     - Использует поведенческие implicit-сигналы (паузы, возвраты, скорость).
  2. **Policy Model (Bandit)**
     - Выбирает тип интервенции в расширенном action space.
     - Оптимизирует reward с учетом `intervention_budget` и delayed эффекта.
  3. **Causal/OPE слой**
     - Логирует `propensity_score` и outcome.
     - Позволяет корректно сравнивать политики без смещения.

### Вехи и контрольные точки

- Неделя 1: зафиксированы гипотезы, KPI и целевые пользовательские сегменты.
- Неделя 3: завершены аудит данных и EDA, утвержден data schema для MVP.
- Неделя 5: готов baseline пайплайн (difficulty + explanations + event logging).
- Неделя 7: завершена offline-оценка и подготовлен A/B-дизайн.
- Неделя 9: MVP выведен в прод/пилот, включен мониторинг retention и unit-экономики.
